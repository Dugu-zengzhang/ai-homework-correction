## 一、缺陷跟踪规程

### 1.1 缺陷编号

- 待处理缺陷：`D-xx`，从 `D-01` 顺序编号。
- 历史已闭环缺陷：`C-xx`，作为「已关闭示例」留档，便于报告展示完整生命周期。

### 1.2 严重级别

| 级别 | 含义 | 准入/关闭要求 |
|------|------|--------------|
| S1 阻塞 | 主链路不可用 / 数据损坏 | 必须立即修复，不得跨版本 |
| S2 严重 | 功能错误 / 安全缺口 / 测试可信度被高估 | 本阶段必须关闭 |
| S3 一般 | 可维护性 / 稳定性隐患 | 按排期修复；未关必须写理由 |
| S4 轻微 | 代码组织问题 | 可挂起，但必须留痕 |

### 1.3 状态流转

```
新建 → 已确认 → 修复中 → 待验证 → 已关闭
                     ↘ 挂起（V1.1）→（后续版本重新进入流转）
```

规则：**不允许「新建直接关闭」**；「已关闭」必须以自动化用例通过或可复现的手工验证为依据。

### 1.4 缺陷单必填字段

| 字段 | 说明 |
|------|------|
| 编号 / 标题 | 唯一编号 + 一句话描述 |
| 严重级别 | S1~S4 |
| 发现人 / 发现时间 | 责任人 + 日期 |
| 环境 | Python 版本、分支、是否依赖外部服务 |
| 复现步骤 | 可据此复现的操作序列 |
| 期望结果 / 实际结果 | 两栏对照 |
| 影响位置 | 文件 + 行号 |
| 负责人 | 修复人 |
| 修复提交 | commit 短哈希（`fix(D-xx)` 前缀） |
| 验证方式 | 自动化用例名或手工步骤 |
| 状态 | 见 1.3 |
