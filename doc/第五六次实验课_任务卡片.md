## 二、缺陷跟踪机制（先定规则，再动手）

| 项 | 约定 |
|----|------|
| **工具选型** | 主用 **GitHub Issues**（仓库已托管，Issue 可直接关联 commit，零成本）；同时维护本地台账 `doc/缺陷跟踪台账.md`（供报告直接引用）。若课程要求指定 Jira / pingCode，把同一批缺陷单**照抄导入**即可，字段一一对应，不重复造数据 |
| **缺陷编号** | `D-01` 起顺序编号；本次评审已闭环的历史缺陷单独用 `C-xx` 编号，作为"已关闭示例" |
| **严重级别** | **S1 阻塞**：主链路不可用／数据损坏；**S2 严重**：功能错误、安全缺口；**S3 一般**：可维护性/稳定性隐患；**S4 轻微**：代码组织问题 |
| **状态流转** | 新建 → 已确认 → 修复中 → 待验证 → 已关闭；跨版本处理记为 **挂起（V1.1）**，挂起必须在台账写明理由 |
| **缺陷单必填字段** | 标题、严重级别、发现人、发现时间、环境（Python 版本/分支）、复现步骤、期望结果、实际结果、影响文件与行号、负责人、修复提交、验证方式、状态 |
| **准入规则** | S1/S2 必须本阶段关闭；S3 按排期，未关必须写理由；S4 可挂起但要留痕 |
| **回归规则** | 每张修复单必须配自动化用例，或写明可复现的手工验证步骤；修复后跑全量回归，结果写进缺陷单 |
